1. Chat Model Fundamentals

Chat Models are the bedrock of LangChain. They represent an abstraction layer that allows developers to interact with various LLMs (GPT, Claude, Gemini) using a unified interface. LangChain v0.2 is the current standard, streamlining these interactions.

Basic Interaction: The `invoke()` Method

The invoke() method is the universal trigger in LangChain. It sends a request to the model and returns a structured response object.

from langchain_openai import ChatOpenAI from dotenv import load_dotenv load_dotenv() # Loads OPENAI_API_KEY from .env model = ChatOpenAI(model="gpt-4o") result = model.invoke("What is 81 divided by 9?") print(result.content) # "9"

Metadata vs. Content: A full result includes metadata (token usage, finish reason, etc.), but result.content extracts only the string response for your application.

2. Prompt Templates

Prompt Templates are the blueprints for LLM inputs. They allow you to decouple the prompt's structure from the specific data being processed, making your code modular and reusable.

The ChatPromptTemplate Powerhouse

In LangChain v0.2/v0.3, ChatPromptTemplate is the standard for building complex message sequences with dynamic placeholders.

from langchain_core.prompts import ChatPromptTemplate from langchain_core.messages import SystemMessage, HumanMessage # Defining a reusable template template = ChatPromptTemplate.from_messages([ ("system", "You are a specialized agent in {topic}."), ("human", "Explain {concept} in {word_count} words."), ]) # Injecting variables prompt_value = template.invoke({ "topic": "Quantum Computing", "concept": "Superposition", "word_count": "50" }) # To see the formatted messages: print(prompt_value.to_messages())

Partial Formatting: You can bind some variables early (e.g., the system persona) and leave others for runtime. This is critical for building template libraries for different specialized agents.

MessagesPlaceholder

For conversational apps, the MessagesPlaceholder is used to dynamically insert the chat history into a template.

from langchain_core.prompts import MessagesPlaceholder template = ChatPromptTemplate.from_messages([ ("system", "You are a helpful assistant."), MessagesPlaceholder(variable_name="history"), ("human", "{input}"), ])

3. Messaging Schema & Logic

Conversations are structured as a List of Messages. To build a dialogue, you must manage different message types:

  • SystemMessage: Sets the behavior/persona and context. Always stays at the top.
  • HumanMessage: Represents the user's input.
  • AIMessage: Represents the model's response.
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage messages = [ SystemMessage(content="You are a professional math tutor."), HumanMessage(content="What is 10 times 5?"), ] result = model.invoke(messages) # To continue the conversation: messages.append(result) # Add the AI response messages.append(HumanMessage(content="Explain how you got that."))

4. Chains & LCEL (LangChain Expression Language)

LCEL is a declarative way to compose chains. It provides a unified interface for streaming, batching, and async support, while allowing you to pipe the output of one component directly into another using the | operator.

The Basic Pipe: Prompt | Model | Parser

The most common chain structure transforms a prompt into a model request, then parses the raw AI output into a clean format.

from langchain_core.output_parsers import StrOutputParser from langchain_core.prompts import ChatPromptTemplate prompt = ChatPromptTemplate.from_template("Tell me a fact about {topic}") model = ChatOpenAI(model="gpt-4o") parser = StrOutputParser() # Creating the chain chain = prompt | model | parser # Execution result = chain.invoke({"topic": "Black Holes"}) print(result) # Directly returns the string content

Standard Interface: Every LCEL chain supports invoke() (sync), ainvoke() (async), stream() (real-time chunks), and batch() (multiple inputs in parallel).

Advanced Composition: Parallel & Passthrough

  • RunnablePassthrough: Used to pass inputs unchanged or combine them with additional context.
  • RunnableParallel: Executes multiple branches simultaneously—perfect for retrieval or multi-model comparisons.
from langchain_core.runnables import RunnableParallel, RunnablePassthrough # Passing input to multiple branches setup_and_retrieval = RunnableParallel( {"context": retriever, "question": RunnablePassthrough()} ) final_chain = setup_and_retrieval | prompt | model | parser

Custom Logic: RunnableLambda

When you need to execute custom Python code that isn't a pre-built LangChain component, use RunnableLambda. It wraps any function into a "Runnable" that can be piped.

from langchain_core.runnables import RunnableLambda # A custom function to clean output def simple_cleaner(text: str): return text.upper().strip() # Wrap and pipe custom_chain = chain | RunnableLambda(simple_cleaner) result = custom_chain.invoke({"topic": "AI"})

6. Enterprise Persistence (Firebase)

In production, you cannot store chat history in local lists—it must be persistent. Using Firebase Firestore allows you to store and retrieve conversation history across sessions.

Persistence Architecture

  • FirestoreChatMessageHistory: Automates the loading and saving of messages to the cloud.
  • Session IDs: Unique identifiers to group messages belonging to a specific user or conversation.
from langchain_google_firestore import FirestoreChatMessageHistory from google.cloud import firestore client = firestore.Client(project="your-project-id") chat_history = FirestoreChatMessageHistory( session_id="user_unique_session_123", collection="chat_history", client=client, ) # Now, any message added is automatically saved to the cloud chat_history.add_user_message("Hello!") chat_history.add_ai_message("How can I help you today?")
Step-by-Step Firebase Setup

1. Create a project at console.firebase.com.

2. Enable Firestore Database in the build tab.

3. Install the GCloud CLI and authenticate using gcloud auth application-default login.

4. Use the project ID and session ID in your LangChain code to start syncing.

1. RAG Foundations

Retrieval-Augmented Generation (RAG) is the paradigm of grounding LLM outputs in verified external data. It solves the "Hallucination" problem by providing the model with a "search engine" for your private documents.

  • Vector Stores: Efficiently storing and retrieving high-dimensional document embeddings (e.g., ChromaDB, Pinecone).
  • Embeddings: Converting text into mathematical vectors that capture semantic meaning.
  • Retrievers: The interface between the model and the vector database, selecting the "Top-K" most relevant chunks.

RAG Architecture & Workflow (Visualized)

Based on the masterclass diagrams and transcript, the RAG architecture is broken down into three critical phases to overcome the knowledge constraints of standard LLMs:

1. Expanding LLM Knowledge

LLMs (like ChatGPT or Gemini) have strict knowledge cut-off dates and no access to your private data. RAG acts as a bridge, allowing you to feed external knowledge sources—such as Websites, PDFs, Code, and Video Transcripts—directly into the LLM's central knowledge base. This eliminates hallucinations and provides up-to-date, specialized answers.

2. Data Ingestion (Chunking & Embedding)

A massive document (e.g., a 10M token PDF) is too large for an LLM's context window (e.g., 8K tokens for ChatGPT). RAG breaks the document into smaller Chunks (e.g., 1K tokens each). These chunks are passed through an LLM Embedder to convert the text into Embeddings—numerical arrays representing semantic meaning (e.g., "dog" and "cat" have similar numerical arrays, whereas "house" is completely different). These embeddings are then stored in a Vector Store.

3. Q&A Retrieval Flow

When a user asks a question, the query itself is converted into an embedding. A Retriever searches the Vector Store to find the most mathematically similar chunks (e.g., finding exact matches for "professor" and "werewolf"). These highly relevant chunks are retrieved and passed directly to ChatGPT alongside the original question, allowing the AI to generate a highly informed, context-aware response based exclusively on the provided documents.

2. Practical Implementation (RAG Basics)

Below is the step-by-step Python implementation of the RAG pipeline discussed above, using LangChain, OpenAI, and ChromaDB. It is divided into two scripts: Data Ingestion and Q&A Retrieval.

Part 1: Data Ingestion (1a_rag_basics.py)

This script loads a text file, splits it into manageable chunks, creates embeddings, and saves them to a persistent Chroma vector database.

import os from langchain.text_splitter import CharacterTextSplitter from langchain_community.document_loaders import TextLoader from langchain_community.vectorstores import Chroma from langchain_openai import OpenAIEmbeddings # Define the directory containing the text file and the persistent directory current_dir = os.path.dirname(os.path.abspath(__file__)) file_path = os.path.join(current_dir, "books", "odyssey.txt") persistent_directory = os.path.join(current_dir, "db", "chroma_db") # Check if the Chroma vector store already exists if not os.path.exists(persistent_directory): print("Persistent directory does not exist. Initializing vector store...") # Ensure the text file exists if not os.path.exists(file_path): raise FileNotFoundError( f"The file {file_path} does not exist. Please check the path." ) # Read the text content from the file loader = TextLoader(file_path) documents = loader.load() # Split the document into chunks text_splitter = CharacterTextSplitter(chunk_size=1000, chunk_overlap=0) docs = text_splitter.split_documents(documents) # Create embeddings and vector store print("\n--- Creating embeddings and vector store ---") embeddings = OpenAIEmbeddings(model="text-embedding-3-small") db = Chroma.from_documents(docs, embeddings, persist_directory=persistent_directory) print("\n--- Finished creating vector store ---") else: print("Vector store already exists. No need to initialize.")

Part 2: Q&A Retrieval (1b_rag_basics.py)

This script loads the previously created persistent database and performs a similarity search to retrieve the most relevant document chunks based on a user's question.

import os from langchain_community.vectorstores import Chroma from langchain_openai import OpenAIEmbeddings # Define the persistent directory current_dir = os.path.dirname(os.path.abspath(__file__)) persistent_directory = os.path.join(current_dir, "db", "chroma_db") # Define the embedding model embeddings = OpenAIEmbeddings(model="text-embedding-3-small") # Load the existing vector store with the embedding function db = Chroma(persist_directory=persistent_directory, embedding_function=embeddings) # Define the user's question query = "Who is Odysseus' wife?" # Retrieve relevant documents based on the query retriever = db.as_retriever( search_type="similarity_score_threshold", search_kwargs={"k": 3, "score_threshold": 0.4}, ) relevant_docs = retriever.invoke(query) # Display the relevant results with metadata print("\n--- Relevant Documents ---") for i, doc in enumerate(relevant_docs, 1): print(f"Document {i}:\n{doc.page_content}\n") if doc.metadata: print(f"Source: {doc.metadata.get('source', 'Unknown')}\n")

Part 3: Document Metadata (2a_rag_basics_metadata.py)

Adding metadata to document chunks allows the LLM to reference exactly where it got the information from (e.g., citing a specific book or source file).

# Iterate through multiple text files and append metadata for book_file in os.listdir(books_dir): if book_file.endswith(".txt"): file_path = os.path.join(books_dir, book_file) loader = TextLoader(file_path) book_docs = loader.load() # Add metadata source for doc in book_docs: doc.metadata["source"] = book_file documents.extend(book_docs) # Now when retrieving, doc.metadata.get('source') will return the specific book name.

Part 4: Text Splitting Deep Dive (3_rag_text_splitting.py)

Explore different chunking strategies. RecursiveCharacterTextSplitter is highly recommended as it preserves natural boundaries like paragraphs and sentences.

from langchain.text_splitter import CharacterTextSplitter, RecursiveCharacterTextSplitter, TokenTextSplitter # 1. Character Splitter (Basic text chunks) char_splitter = CharacterTextSplitter(chunk_size=1000, chunk_overlap=100) # 2. Recursive Character Splitter (Highly Recommended - splits around natural boundaries) recursive_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100) # 3. Token Splitter (Splits strictly by AI token count) token_splitter = TokenTextSplitter(chunk_size=1000, chunk_overlap=100)

Part 5: Embedding Deep Dive (4_rag_embedding.py)

Switch between powerful API-based models (OpenAI) and free, open-source models that run locally (Hugging Face).

from langchain_openai import OpenAIEmbeddings from langchain_community.embeddings import HuggingFaceEmbeddings # 1. OpenAI Embeddings (Highly accurate, requires API key) openai_embeddings = OpenAIEmbeddings(model="text-embedding-3-small") # 2. Hugging Face Embeddings (Free, runs locally, trades off some accuracy for zero API cost) huggingface_embeddings = HuggingFaceEmbeddings( model_name="sentence-transformers/all-MiniLM-L6-v2" )

Part 6: Retriever Deep Dive (5_rag_retriever.py)

Optimize how you query the vector store by fine-tuning the search parameters.

# 1. Similarity Score Threshold (Only returns chunks above a 40% match threshold) retriever = db.as_retriever( search_type="similarity_score_threshold", search_kwargs={"k": 3, "score_threshold": 0.4} ) # 2. Max Marginal Relevance (MMR) # Balances returning similar documents with diversifying the results to capture broader context mmr_retriever = db.as_retriever( search_type="mmr", search_kwargs={"k": 3, "lambda_mult": 0.5} )

3. Conversational RAG

Managing History-Aware Retrieval

Standard RAG takes a single query and returns results. Conversational RAG requires the model to understand the *entire* dialogue history to reformulate queries for the vector store.

The Core Loop: Chat History + New Question → Reformulated Query → Vector Search → Grounded Answer.

# History-Aware Retriever Prompt contextualize_q_system_prompt = ( "Given a chat history and the latest user question " "which might reference context in the chat history, " "reformulate a standalone question which can be understood " "without the chat history." )
  • Create Stuff Documents Chain: A LangChain utility that "stuffs" all retrieved documents into a single prompt for the LLM.
  • History-Aware Retriever: Re-phrases the user question based on previous turns to ensure the vector lookup is accurate even with pronouns like "it" or "him".

4. Advanced Web Scraping

Building a RAG system often starts with data collection. LangChain provides multiple loaders, but not all are created equal.

Standard WebLoader

Basic HTML extraction. Often misses dynamic content rendered via JavaScript and includes messy boilerplate (headers, footers).

Firecrawl Loader

Converts websites into clean, LLM-ready Markdown. Handles dynamic JS rendering and provides superior chunking metadata.

Why Firecrawl?

Firecrawl turns the "gross" HTML into a markdown version that is easy for LLMs to navigate. It uses a "crawl" vs "scrape" mode—crawl follows links to map a site, while scrape targets a specific page depth.

Implementation: Web Scraping Pipeline

The pipeline remains identical to loading a local text file, except we swap the TextLoader with a web-based loader.

import os from langchain_community.document_loaders import WebBaseLoader, FireCrawlLoader from langchain.text_splitter import RecursiveCharacterTextSplitter from langchain_community.vectorstores import Chroma from langchain_openai import OpenAIEmbeddings # 1. Initialize the Loader (Choose One) # Option A: Standard Web Loader # loader = WebBaseLoader("https://apple.com") # Option B: Firecrawl Loader (Superior for clean Markdown) loader = FireCrawlLoader( api_key=os.getenv("FIRECRAWL_API_KEY"), url="https://apple.com", mode="scrape" ) # 2. Load and extract the website content documents = loader.load() # 3. Split the extracted content into chunks text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100) docs = text_splitter.split_documents(documents) # 4. Embed and store in a persistent Vector Database embeddings = OpenAIEmbeddings(model="text-embedding-3-small") persistent_directory = os.path.join(os.path.dirname(__file__), "db", "apple_db") db = Chroma.from_documents(docs, embeddings, persist_directory=persistent_directory) # 5. Query the newly created Web-Scraped Database retriever = db.as_retriever( search_type="similarity_score_threshold", search_kwargs={"k": 3, "score_threshold": 0.4} ) relevant_docs = retriever.invoke("What are the latest features of the iPhone?") print(relevant_docs)

5. Autonomous Agents

To understand Agents in simple English, think of a standard LLM (like ChatGPT) as a highly intelligent brain trapped in a box. It can write essays and answer questions based on its training data, but it cannot do anything in the real world.

An Autonomous Agent is when you take that brain, give it a checklist (a goal), and give it a pair of hands (tools) so it can interact with the outside world. Instead of just giving you an answer right away, the Agent is allowed to stop, think, use a tool, read the result, and then think again until it solves your problem.

The ReAct Loop (Reason + Act)

The core engine behind how an Agent thinks is called the ReAct framework. It works in a continuous loop:

  • Thought (Reasoning): "The user wants to know the current weather in Paris. I don't know the current weather because my training data is old. I need to look it up."
  • Action (Acting): The agent decides to use the "Weather Search Tool" and types in "Paris".
  • Observation: The tool returns: "It is currently 22°C and sunny in Paris."
  • Next Thought: "I now have the answer. I will give it to the user."

Agent Executor: This is the "manager" program that watches the Agent. It makes sure the Agent doesn't get stuck in an infinite loop and handles the actual passing of data between the Agent's brain and the Tools.

6. Tools: The Agent's Superpowers

If the Agent is the brain, Tools are the hands, eyes, and ears. Without tools, an Agent is just a chatbot. Tools allow the Agent to browse the web, read your private database, run Python code, or even send emails on your behalf.

How do Tools work?

You cannot just hand a Python script to an AI and expect it to know how to use it. You have to clearly explain the tool to the AI. You do this by providing a strict set of rules (a schema) that tells the AI: "Here is what this tool does, and here are the exact variables you need to provide to make it work."

Types of Tools in LangChain

  • The @tool Decorator (Simple): The easiest way. You just take a normal Python function, add @tool above it, and write a very clear docstring. The LLM reads that docstring to figure out what the function does.
  • Structured Tools (Advanced): Used for complex tools that require multiple inputs. We use Pydantic (a data validation library) to force the LLM to provide inputs in the exact right format (e.g., forcing it to provide both a 'city' and a 'date' for a weather tool).
  • BaseTool Inheritance (Expert): Creating a custom tool class from scratch. This gives you maximum control over how the tool handles errors or runs in the background.

Implementation 1: Basic Python Function Tool

Here is a complete example of how to build a simple tool using the @tool decorator, and then pass it to an Agent so the LLM can answer questions about the real world.

from langchain_openai import ChatOpenAI from langchain.agents import tool, create_tool_calling_agent, AgentExecutor from langchain_core.prompts import ChatPromptTemplate # 1. Create a Simple Tool @tool def get_system_time(format_string: str = "%Y-%m-%d") -> str: """Returns the current system date and time. Use this whenever the user asks for the current time or date.""" import datetime return datetime.datetime.now().strftime(format_string) tools = [get_system_time] # 2. Initialize the LLM (The Brain) llm = ChatOpenAI(model="gpt-4o", temperature=0) # 3. Create the Prompt and Agent prompt = ChatPromptTemplate.from_messages([ ("system", "You are a helpful assistant. Use the provided tools when necessary."), ("human", "{input}"), ("placeholder", "{agent_scratchpad}") # This is where the Agent stores its 'Thoughts' ]) agent = create_tool_calling_agent(llm, tools, prompt) # 4. Run the Agent using the Executor (The Manager) agent_executor = AgentExecutor(agent=agent, tools=tools, verbose=True) # 5. Ask a question that requires the tool response = agent_executor.invoke({"input": "What is the exact date today?"}) print(response["output"])

Concept: What is Pydantic?

Before building advanced tools, you need to understand Pydantic—a data validation library for Python. Instead of writing long __init__ methods, you simply define the expected data types. Pydantic automatically validates the data under the hood. In LangChain, we use Pydantic to strictly enforce exactly what arguments the LLM is allowed to pass to our tools.

Normal Python Class
class User: def __init__(self, name: str, age: int, email: str): self.name = name self.age = age self.email = email
Using Pydantic (BaseModel)
from pydantic import BaseModel, EmailStr class User(BaseModel): name: str age: int email: EmailStr

Advanced: Custom Structured Tools (BaseTool)

For more complex tools, we inherit from BaseTool and use Pydantic to strictly enforce what data types the LLM is allowed to pass.

# Custom Tool with Pydantic Schema from langchain_core.tools import BaseTool from pydantic import BaseModel, Field class MultiplyNumbersInput(BaseModel): a: float = Field(description="First number") b: float = Field(description="Second number") class MultiplyTool(BaseTool): name = "multiply_numbers" description = "Useful for multiplying two numbers." args_schema = MultiplyNumbersInput def _run(self, a: float, b: float): return a * b

7. OpenAI Function Calling

Once you understand Pydantic, you can use it to strictly format the outputs of OpenAI models by binding functions directly to the LLM. This is the underlying mechanism that powers most agentic tool usage.

1. Converting Pydantic to OpenAI Functions

LangChain provides a utility to automatically convert your Pydantic schemas into the exact JSON format that OpenAI's API expects for function calling.

from langchain.utils.openai_functions import convert_pydantic_to_openai_function from pydantic import BaseModel, Field class WeatherSearch(BaseModel): """Call this with an airport code to get the weather at that airport""" airport_code: str = Field(description="airport code to get weather for") # Converts the Pydantic class into OpenAI's required JSON schema weather_function = convert_pydantic_to_openai_function(WeatherSearch)

2. Binding Functions to the Model

You can bind one or multiple functions to the chat model. The LLM will automatically decide which function to trigger based on the user's prompt.

from langchain.chat_models import ChatOpenAI model = ChatOpenAI() model_with_functions = model.bind(functions=[weather_function, artist_search_function]) # The LLM dynamically decides to trigger 'WeatherSearch' model_with_functions.invoke("what is the weather in sf?") # The LLM dynamically decides to trigger 'ArtistSearch' model_with_functions.invoke("what are three songs by taylor swift?") # If no function is needed, it just talks normally model_with_functions.invoke("hi!")

3. Forcing a Specific Function

Sometimes you don't want to leave it up to the LLM. You can explicitly force the model to use a specific function, guaranteeing structured output.

# Force the model to always use the WeatherSearch function model_with_forced_function = model.bind( functions=[weather_function], function_call={"name":"WeatherSearch"} ) # Even if the user says "hi!", the model will try to extract an airport code model_with_forced_function.invoke("hi!")

4. Using Bound Models in LCEL Chains

Models bound with functions can be used seamlessly in standard LCEL chains, ensuring structured data extraction at any step of your pipeline.

from langchain.prompts import ChatPromptTemplate prompt = ChatPromptTemplate.from_messages([ ("system", "You are a helpful assistant"), ("user", "{input}") ]) chain = prompt | model_with_functions chain.invoke({"input": "what is the weather in sf?"})

7. Multi-Agent Systems (CrewAI)

The future of AI is collaborative. Instead of one monolithic agent, we use specialized agents working together.

  • Specialization: A "Researcher" agent finds data, while a "Writer" agent synthesizes it.
  • Collaboration: Agents can delegate tasks to each other, reviewing and refining outputs in a structured workflow.
  • CrewAI: A framework that simplifies multi-agent orchestration, allowing you to define "Crews" with processes and roles.
